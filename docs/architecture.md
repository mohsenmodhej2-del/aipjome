# معماری پروژه فروشگاه همه‌چی

این برنامه یک **Modular Monolith** است: یک واحد قابل استقرار و یک پایگاه‌دادهٔ SQLite/D1 دارد، اما منطق کسب‌وکار به ماژول‌های مستقل تقسیم شده است.

## جهت وابستگی

```text
UI / app pages
      |
HTTP adapters / app/api (validation, cookie, response)
      |
Application modules / modules/* (use-cases and policies)
      |
Core + SQLite/D1
```

Routeهای HTTP اجازهٔ اجرای SQL یا import مستقیم زیرساخت دیتابیس را ندارند. این مرز با `npm run check:architecture` کنترل می‌شود. ماژول‌ها نیز نباید به پوشهٔ `app` وابسته باشند.

## ماژول‌ها

- `identity`: ثبت‌نام، ورود و نشست کاربر
- `access`: نقش‌ها، محدودهٔ دسته‌ای و واگذاری دسترسی
- `catalog`: دسته، کالا و گونه‌های کالا
- `orders`: ثبت و مشاهدهٔ سفارش
- `payments`: تأیید درگاه فرضی و تکمیل تراکنش خرید
- `fulfillment`: تفکیک و پیگیری ارسال برای هر دامنهٔ کالایی
- `invoices`: صدور و نمایش فاکتور
- `support`: درخواست‌های مشتری و پاسخ مدیر دامنه
- `dashboard`: نمای ترکیبی پنل مدیریت
- `audit`: ثبت رویدادهای حساس
- `core`: اتصال دیتابیس، خطاها و امنیت پایه
- `bootstrap`: داده‌های نمایشی اولیه

## تراکنش خرید

سفارش ابتدا در وضعیت انتظار پرداخت ساخته می‌شود. ماژول پرداخت فرضی پس از تأیید، موجودی را کم می‌کند، سفارش را پرداخت‌شده می‌کند، برای هر دسته یک fulfillment می‌سازد و شمارهٔ فاکتور پایدار صادر می‌کند. این آداپتر بعداً می‌تواند با درگاه واقعی جایگزین شود، بدون تغییر UI یا منطق سفارش.

## تصمیم استقرار

در این مرحله، یک استقرار و SQLite/D1 انتخاب شده تا تراکنش‌ها، توسعه و عملیات ساده بماند. مرزهای ماژولی امکان جداکردن سرویس‌های پرترافیک در آینده را فراهم می‌کنند، اما فعلاً هزینه و پیچیدگی microservice تحمیل نمی‌شود.
